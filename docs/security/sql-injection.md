# SQLインジェクション

ユーザーからの入力値を、そのままSQL文の一部として組み立てて実行してしまうことで、意図しないクエリを実行されてしまう脆弱性です。

## 発生する条件

以下がそろったときに発生します。

1. ユーザー入力（フォーム、URLパラメータ、Cookieなど）をSQL文に含めている
2. 入力値を「**文字列連結**」でクエリに埋め込んでいる（プレースホルダ・バインド変数を使っていない）
3. 入力値に対するエスケープ・検証が不十分

典型的な脆弱なコード（擬似コード）:

```js
const query = `SELECT * FROM users WHERE username = '${username}' AND password = '${password}'`
db.execute(query)
```

`username` や `password` に `'`（シングルクォート）を含む文字列を入力すると、クエリの文字列としての境界が壊れ、SQL文の構造そのものを書き換えられます。

### 何が起きたか

パスワード欄に `' OR '1'='1` を入力すると、組み立てられるクエリは次のようになります。

```sql
SELECT * FROM users WHERE username = 'alice' AND password = '' OR '1'='1'
```

`password = ''` の部分で閉じたつもりの条件式に `OR '1'='1'` が追加され、WHERE句全体が常に真になります。結果として、パスワードの正誤に関わらず全行が条件にマッチし、データが漏洩したり認証がバイパスされたりします。

`--` や `#` を使ってクエリの残り部分をコメントアウトする、複数のクエリを `;` で連結して実行する（スタックドクエリ）など、応用的な攻撃パターンも同じ「入力値がクエリ構造に影響する」という原理から生まれます。

## 対策

### 1. プレースホルダ（プリペアドステートメント）を使う

最も確実な対策です。値は常に「データ」として扱われ、クエリの構造に影響を与えません。

```js
const query = `SELECT * FROM users WHERE username = ? AND password = ?`
db.execute(query, [username, password])
```

デモの「安全な実装」モードで同じ入力を試すと、`' OR '1'='1` はただの文字列として扱われ、条件にマッチせずログインが失敗することが確認できます。

### 2. ORMやクエリビルダを使う

多くのORM（Prisma, TypeORM, SQLAlchemyなど）は内部的にプレースホルダを使うため、素のSQLを書くより安全になりやすいです。ただし `raw()` 系のAPIで生SQLを文字列連結すると同じ問題が起こり得るので注意が必要です。

### 3. 最小権限の原則

アプリケーションが使うDBユーザーの権限を必要最小限にしておくことで、万が一インジェクションが発生しても被害範囲を抑えられます。

### 4. 入力値のバリデーション

エスケープやバリデーションは補助的な対策にはなりますが、これだけに頼るのは危険です。抜け漏れが起きやすいため、あくまでプレースホルダと併用します。
