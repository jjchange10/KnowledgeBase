# CSRF（クロスサイトリクエストフォージェリ）

ログイン済みのユーザーのブラウザに、本人の意図しないリクエストを（別サイト経由で）送信させることで、送金や退会、設定変更などの操作を勝手に実行させてしまう脆弱性です。

## 発生する条件

以下がそろったときに発生します。

1. ログイン状態がCookie（セッションID）だけで維持されている
2. 状態変更を伴うリクエスト（送金、パスワード変更など）が、Cookie以外にリクエストの正当性を検証する仕組みを持たない
3. 攻撃者が用意した別サイトへユーザーを誘導できる（リンク、画像タグ、自動送信フォームなど）

ブラウザは、リクエスト先のドメインに紐づくCookieを、**リクエスト元のページが同一オリジンかどうかに関わらず**、自動的に付与します。この挙動を悪用し、攻撃者は自分のサイトに次のような自動送信フォームを仕込みます。

```html
<form action="https://bank.example.com/transfer" method="POST">
  <input type="hidden" name="to" value="attacker" />
  <input type="hidden" name="amount" value="5000" />
</form>
<script>document.forms[0].submit()</script>
```

ログイン中のユーザーがこのページを開くと、ブラウザは自動的に銀行サイトのセッションCookieを付けてPOSTリクエストを送信します。サーバー側がCookieの有無しか見ていなければ、これを「本人の正規のリクエスト」として処理してしまいます。

### 何が起きたか

サーバー（を模した処理）が、リクエストに正しいセッションが付いているかどうかしか確認していなかったため、攻撃者のページから送信された偽のリクエストも「本人の操作」として受理されてしまいました。

## 対策

### 1. CSRFトークンを使う

サーバーが発行したランダムなトークンをフォームに埋め込み、リクエスト時にそのトークンも一致するか検証します。攻撃者のページはこのトークンの値を知る手段がないため、偽のリクエストを作れません。デモの「安全な実装」がこれにあたります。

### 2. Cookieに `SameSite` 属性を設定する

`SameSite=Lax` または `Strict` を設定すると、他サイトからのナビゲーションで発生するリクエストにCookieが付与されなくなり、多くのCSRF攻撃を防げます。近年のブラウザはデフォルトを `Lax` にしています。

### 3. 重要な操作ではCookie以外の検証を追加する

パスワード変更や退会など影響の大きい操作では、直前のパスワード再入力や確認画面を挟むことで、たとえリクエストが偽造されても被害を防ぎやすくなります。

### 4. カスタムヘッダーを要求する（API向け）

`X-Requested-With` のようなカスタムヘッダーを必須にする方法も有効です。単純な `<form>` タグによる送信ではカスタムヘッダーを付けられないため、クロスオリジンからの偽装リクエストを防げます（CORS設定と合わせて検討が必要です）。
