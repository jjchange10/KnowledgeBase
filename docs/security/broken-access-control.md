# 認可不備（IDOR / Broken Access Control）

「ログインしているかどうか」は確認していても、「そのリソースに対して操作する権限があるか」を確認していないことで、URLやパラメータのIDを変えるだけで他人のデータにアクセス・改ざんできてしまう脆弱性です。IDOR（Insecure Direct Object References）とも呼ばれます。

## 発生する条件

以下がそろったときに発生します。

1. リソースをIDで直接指定してアクセスしている（`/api/orders/123` のようなURLなど）
2. サーバー側が「ログイン済みかどうか」しか見ておらず、「そのIDのリソースがログインユーザー自身のものか」を確認していない
3. IDが連番や推測しやすい値になっている（UUIDであっても、所有者チェックがなければ根本的な対策にはならない）

典型的な脆弱なコード（擬似コード）:

```js
app.get('/api/orders/:id', (req, res) => {
  const order = db.orders.find(o => o.id === req.params.id)
  // ログインチェックはしているが、order.owner と req.user を比較していない
  res.json(order)
})
```

ログインさえしていれば、URLの `id` を書き換えるだけで他人の注文情報を閲覧できてしまいます。

### 何が起きたか

サーバー（を模した処理）は指定されたIDのレコードが存在するかどうかだけを確認し、そのリソースがリクエストしたユーザー自身のものかどうかを確認していませんでした。ログイン機能自体は正しく動いていても、この「認可（authorization）」のチェックが抜けていると被害が発生します。

## 対策

### 1. リソースを返す前に必ず所有者を確認する

「認証（authentication）＝誰であるか」と「認可（authorization）＝何をしてよいか」は別物です。IDでリソースを取得したら、必ず `resource.owner === currentUser.id` のような所有者チェックを行います。デモの「安全な実装」がこれにあたります。

### 2. IDをユーザーのスコープに閉じ込める

可能であれば、クエリ自体を `WHERE id = ? AND user_id = ?` のようにユーザーでスコープした形で発行し、そもそも他人のレコードが取得結果に含まれないようにします。

### 3. 権限チェックを共通化する

エンドポイントごとに個別に権限チェックを書くと抜け漏れが発生しやすいため、認可ロジックをミドルウェアやポリシーレイヤーとして共通化し、新しいエンドポイントを追加する際にも必ず通るようにします。

### 4. 推測しにくいIDを使うことは補助策として

連番IDをUUIDにするなどは推測によるアクセスを難しくしますが、所有者チェックの代わりにはなりません。あくまで多層防御の一部として位置づけます。
