# XSS（クロスサイトスクリプティング）

ユーザーが入力した文字列を、エスケープせずにそのままHTMLとして画面に描画してしまうことで、攻撃者が仕込んだHTML/JavaScriptが他のユーザーのブラウザ上で実行されてしまう脆弱性です。

## 発生する条件

以下がそろったときに発生します。

1. ユーザー入力（コメント、プロフィール、検索キーワードなど）を画面に描画している
2. 描画時にHTMLとして解釈させている（エスケープしていない／`innerHTML` や `v-html` などを使っている）
3. 入力値に対するサニタイズが不十分

典型的な脆弱なコード（擬似コード）:

```js
// React
element.innerHTML = userComment

// Vue
// <div v-html="userComment"></div>
```

`userComment` に `<script>` や `<img onerror=...>` のようなタグを含む文字列が入っていると、そのままブラウザに解釈され実行されます。

### 主な種類

- **反射型（Reflected）**: URLパラメータなどの入力値がそのままレスポンスに含まれ、実行される。攻撃者は悪意あるリンクを踏ませる必要がある。
- **格納型（Stored）**: コメントやプロフィールなど、DBに保存された入力値が他のユーザーに表示されるたびに実行される。被害範囲が広い。
- **DOM based**: サーバーを経由せず、クライアント側のJavaScriptが `location.hash` などの値をそのままDOMに書き込むことで発生する。

### 何が起きたか

投稿された文字列が `v-html`（≒ `innerHTML`）でそのままDOMに挿入されたため、`<img src="x" onerror="...">` の `onerror` ハンドラがブラウザによって実行されました。

実際の攻撃では、ここで `document.cookie` を攻撃者のサーバーに送信してセッションを乗っ取ったり、ページの内容を書き換えてフィッシングを行ったりします。タブタイトルの書き換えは、その一例を安全な形で示したものです。

## 対策

### 1. 出力時に必ずエスケープする

多くのフレームワーク（React, Vue, Angularなど）は、デフォルトでテキストとして出力する限り自動的にエスケープします。デモの「安全な実装」がこれにあたります。`innerHTML` や `v-html`、`dangerouslySetInnerHTML` のように明示的にHTMLとして扱うAPIを避けるのが基本です。

### 2. どうしてもHTMLを描画する必要がある場合はサニタイズする

リッチテキストエディタの出力など、HTMLそのものを描画したいケースでは、DOMPurifyのような信頼できるサニタイズライブラリを通してから描画します。

### 3. Content Security Policy (CSP) を設定する

CSPヘッダーでインラインスクリプトの実行や外部スクリプトの読み込み元を制限しておくと、万が一エスケープ漏れがあっても被害を軽減できます。

### 4. Cookieに `HttpOnly` を付与する

セッションCookieに `HttpOnly` を付けておくと、たとえXSSが発生してもJavaScriptから `document.cookie` を読み取れなくなり、セッションハイジャックを防げます。
