# セッション

HTTPは本来「ステートレス」なプロトコルで、1つ1つのリクエストは独立しており、サーバーは「さっきのリクエストを送ってきたのが誰か」を自動的には覚えていません。ログイン状態を維持するなど、複数のリクエストをまたいでユーザーの状態を保持する仕組みが**セッション**です。

## 仕組み

典型的なセッションベース認証は次のような流れになります。

```
Client                              Server
  |  POST /login (id, password)        |
  |------------------------------------>|
  |                                     | 認証成功 → セッションを生成
  |                                     | session store: { "abc123": {userId: 1} }
  |  Set-Cookie: sessionId=abc123       |
  |<------------------------------------|
  |                                     |
  |  GET /mypage                        |
  |  Cookie: sessionId=abc123           |
  |------------------------------------>|
  |                                     | session store を sessionId=abc123 で検索
  |                                     | → userId=1 のページを返す
  |  200 OK (マイページのHTML)          |
  |<------------------------------------|
```

1. ログイン成功時、サーバーはランダムな**セッションID**を発行し、サーバー側のストア（メモリ、Redis、DBなど）に `セッションID → ユーザー情報` を保存する
2. サーバーはレスポンスの `Set-Cookie` ヘッダーでセッションIDをブラウザに渡す
3. ブラウザは以降の同じサイトへのリクエストに、自動的にそのCookieを付けて送る（[Cookie](/web-basics/cookie) を参照）
4. サーバーは受け取ったセッションIDでストアを検索し、「誰からのリクエストか」を特定する

ユーザー情報そのものはサーバー側に保持され、クライアントが持っているのは「参照キー」であるセッションIDだけ、という点がポイントです。

## いつ使うか

- ログイン状態の保持
- ショッピングカートの中身の保持
- 複数ページにまたがるフォーム入力の一時保存

## 気をつけること

- **セッションハイジャック**: セッションIDが漏洩すると、そのIDを使って他人になりすませてしまいます。[XSS](/security/xss)でCookieを盗まれたり、通信を盗聴されたりするのが典型的な経路です。`HttpOnly` や `Secure` 属性、HTTPS化が対策になります。
- **セッション固定化（Session Fixation）**: ログイン前のセッションIDをログイン後もそのまま使い回すと、攻撃者が事前に用意したセッションIDを踏ませることでなりすましが可能になります。ログイン成功時にセッションIDを再発行するのが対策です。
- **有効期限**: セッションには適切なタイムアウトを設定し、使われなくなったセッションはサーバー側でも破棄します。

## JWTベースの認証との違い

近年のAPIサーバーでは、サーバー側にセッションを保持せず、ユーザー情報を含めた署名付きトークン（JWTなど）をクライアントに持たせる方式もよく使われます。サーバー側の状態管理が不要になりスケールしやすい一方、発行したトークンを即座に失効させるのが難しいというトレードオフがあります。
